# Agent Note: 邀请注册与传播限制

Status: implemented

[English](2026-08-26-invitation-registration.md) | 中文

## Problem

开放注册允许任何网络调用者创建小薇账号，并持续消耗托管模型与存储资源。部署级共享密码或统一邀请码无法把邀请行为归属到具体账号，也无法限制传播规模；单个凭证泄露后只能影响所有用户。

## Decision

身份提供方在身份数据库中管理分享码记录。分享码兑换、账号插入与最终人数检查在同一个 SQLite 写事务中完成。小薇默认将账号总数限制为 100 个，引导账号和现有账号都计入；每个账号终身可以生成三个一次性分享码。被邀请人注册后使用自己的密码登录，并获得独立的三个分享码名额。

分享码生成、列表与重新生成需要经过认证的账号主体，所有者始终从该主体派生。存储保留用于兑换的 HMAC-SHA256 摘要，以及供所有者再次查看的 AES-256-GCM 密文。加密密钥通过带域分离的 HKDF-SHA256 从分享码 pepper 派生，认证数据将密文绑定到分享码标识与所有者标识。pepper 可以由配置提供；未配置时，文件数据库提供方会在数据库旁原子创建一个仅所有者可读的密钥文件。

只有在分享码未使用、未过期且具有加密明文时，所有者的分享码列表才返回完整值。已使用和已过期的记录只返回掩码元数据。启用加密存储前创建的记录保持掩码，因为 HMAC 摘要不能恢复原值。所有者可以明确重新生成这类仍有效的记录；重新生成会原地替换摘要、后缀和密文，使旧值失效，但不会再消耗一个终身分享码名额。

注册邮箱验证码按规范化邮箱、注册用途和分享码标识共同确定。公开的邮箱验证码预检会在发送前拒绝不可用的分享码，注册时再验证同一组绑定关系，然后进入身份事务。桌面端注册表单要求填写分享码；登录后的账户设置持续展示并允许复制有效分享码，重新生成旧版分享码前需要确认。

## Alternatives considered

**每次登录都要求分享码。** 这会让分享码成为共享的第二密码，无法干净地按账号撤销，并迫使接收者长期保存注册时已经消耗的凭证。

**把分享码放在独立提供方数据库中。** 两个 SQLite 数据库不能原子地消耗分享码并创建账号。预留与补偿会增加可恢复的中间状态，却不能改善当前单机部署。

**分享码过期后返还名额。** 可回收名额允许无限生成分享码，使三人传播限制失去明确含义。终身生成次数便于检查。

**直接存储分享码明文。** 明文存储会使数据库副本足以兑换所有有效分享码。认证加密既保留所有者重复查看能力，又不接受这种暴露。

**自动重新生成旧版分享码。** 静默重新生成会使所有者可能已经分享的值失效。明确操作把这一破坏性选择留给所有者。

## Consequences

该设计提供可归属、可限制的邀请传播，并同时防止分享码重复使用和人数上限竞态。现有账号和引导账号占用人数名额并获得分享码额度，因此已有 100 个账号的数据库不能再生成或兑换分享码。过期或其他未使用的分享码仍占用所有者的终身名额。

所有者可以重复查看有效分享码，因此分发更方便，同时不会削弱一次性使用、有效期、账号所有权和终身生成限制。仅数据库泄露不会直接暴露分享码，但数据库与分享码 pepper 同时泄露时，攻击者可以解密有效值。因此访问控制和备份处理仍是安全措施的一部分。

按照仓库的预发布策略，身份数据库 schema 版本 3 会明确拒绝已有的版本 2 数据库。因此部署这份源码前，需要另行授权并备份、执行增加可空密文列的离线迁移；迁移后的旧版记录仍保持掩码。随后还需完成 SMTP 与已安装客户端验收，因为源码级验证不能证明这些层级。
